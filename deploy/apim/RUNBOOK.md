# WSO2 API Manager: blue/green move to persistent state + native analytics

Namespace `apim` on the VM. Two instances of the same image (`wso2/wso2am:4.5.0`) run side by side:

| | blue (old) | green (new) |
|---|---|---|
| Deployment / pod label | `wso2am` / `app: wso2am` | `wso2am-green` / `app: wso2am-green` |
| Configuration | ConfigMap `apim-conf` | ConfigMap `apim-conf-green` (blue's config + 3 changes, see below) |
| State | embedded H2 inside the container, lost on any restart | PVC `wso2am-green-data` (5Gi, `local-path`) |
| Analytics | off | on, `apim_metrics.log` in `/var/log/weave/apim` on the host |
| Own ports | - | Service `wso2am-green`: 31443 (mgmt), 31243 (gateway https), 31280 (gateway http) |

The public ports 30443 / 30243 / 30280 belong to Service `wso2am`. Which instance is live is decided
only by that Service's selector. Current state: `cat /root/apim-bluegreen/STATUS` and
`bash deploy/apim/scripts/switch.sh status`.

## Rollback (one command, takes effect within a second)

    kubectl -n apim patch svc wso2am --type merge -p '{"spec":{"selector":{"app":"wso2am"}}}'

or `bash deploy/apim/scripts/switch.sh blue` (same patch, plus a line in the action log).
Blue was never stopped or changed, so it answers at once with the state it had at the switch.
Everything created on green after the switch (APIs, applications, keys, sign-ins) is not on blue.
Going forward again: `bash deploy/apim/scripts/switch.sh green` if nothing was changed on blue in
between (green keeps its newer state), otherwise decide which side's changes to keep; `reseed.sh`
+ `go_live.sh` (below) rebuild green from blue.

## What was done

1. Recorded blue (Deployment, Service, ConfigMap, REST state) in `/root/apim-bluegreen/blue/` and
   `truth/`. Nothing on blue was changed, restarted or scaled at any point.
2. `scripts/snapshot.sh`: copied blue's five H2 files out of the running pod (`cat` only),
   checksummed inside the pod before and after the copy; repeated until nothing moved.
   `scripts/validate.py`: opened the copy with the H2 jar that ships in the image (pod `apim-tools`),
   read every row of every database, and compared APIs, applications, subscriptions, keys,
   revisions, gateway artifacts, policies and key managers with what blue's REST APIs report.
3. Started green from `green/*.yaml`. An init container copies the validated snapshot onto the
   volume only if the volume holds no database, verifies the checksums, and refuses to start APIM
   with blank databases. On every later start it leaves the volume alone.
4. `scripts/gate.py` (69 checks) on green's own ports, compared with blue: identical REST state,
   every API published and deployed, same DCR client, same consumer key and secret for
   `aroya-connector`, tokens issued, every API context answering exactly like blue on both gateway
   ports (no token, invalid token, valid token, token issued by the other instance), consoles, OIDC
   discovery, same signing key, sign-in request of both Weave consoles accepted, one analytics event
   per request, logs readable as uid 1000, blue untouched, green never connecting to blue.
   Then the green pod was deleted once and the gate repeated, plus `scripts/persist_probe.py`
   (a refresh token issued before the restart is still redeemable after it).
5. `scripts/go_live.sh`: fresh snapshot of blue compared with green's seed, selector patched, blue
   checked once more, the same gate repeated on the real ports, both Weave consoles checked
   (`/healthz` 200, sign-in redirect reaches APIM and its login page). Any failure switches back.

   Afterwards the seed is disarmed (`seed/VALIDATED` renamed to `CONSUMED`).

What actually happened on 2026-11-14 (UTC): green was first seeded from a snapshot taken 19:52:46
and passed both gates. The check before the switch then found that another stream had meanwhile
created a test API (`weave-sample-ship-list`), an application with a key (`weave-studio-test`) and
a DCR client (`weave-runtime`) on blue, so `go_live.sh` refused. `reseed.sh` rebuilt green from a
snapshot taken 20:10:37 (gates passed again, 77/77 including the test API), `go_live.sh` switched
at 20:17:34, the post-switch gate passed and the runtime resync answered 200. The green pod
that went live was deleted and restarted once before the switch (the earlier build twice) and came
back complete every time.

Every mutating command is in `/root/apim-bluegreen/actions.log`; gate reports are
`/root/apim-bluegreen/gate-*.txt`.

## Differences between green and blue

Generated by `scripts/green_config.py` from blue's live ConfigMap, so nothing else can drift:

- `[apim.analytics] enable = true`, `type = "elk"`: WSO2's native analytics publisher writes one
  line per gateway request (also rejected ones) to `repository/logs/apim_metrics.log`.
- `[indexing] re_indexing = 1`: the registry search index is not part of the database snapshot, so
  green rebuilds it on its first boot. The index then lives on the volume.
- `[http_access_log] maxDays = 14`.
- `log4j2.properties` (`scripts/patch_log4j2.py` applied to the image's file): every date-rolled
  log deletes its rolled files after 14 days or above a size cap (analytics 2 GB, gateway access
  1 GB, carbon 500 MB, others 200 MB); analytics and gateway access logs roll at 100 MB.
- Deployment: PVC, log directory on the host, startup/readiness/liveness probes, a `preStop` hook
  that stops the JVM cleanly (the image's entrypoint does not forward SIGTERM), `Recreate` strategy.

`green/deployment.toml.template` is green's configuration with every credential replaced by
`<SET-ME:...>`. The real file exists only in ConfigMap `apim-conf-green` and in
`/root/apim-bluegreen/green/` (mode 700). Never commit it.

## Where things live

- Volume: PVC `wso2am-green-data` = a directory under `/var/lib/rancher/k3s/storage/` on the node
  (`kubectl -n apim get pv`). `database/` H2 files, `solr/` search index, `security/` keystores.
- Logs: `/var/log/weave/apim/` on the host, owner uid 10001, world-readable. `apim_metrics.log`
  (analytics events), `http_access.log` (gateway access), `http_access_.<date>.log` (management
  access), `wso2carbon.log`, `audit.log`, `api.log`. Weave Gateway (uid 1000) needs this directory
  mounted read-only at the path its `APIM_LOG_DIR` names.
- Work directory: `/root/apim-bluegreen/` (mode 700): `STATUS`, `actions.log`, `seed/` (the
  snapshot green was seeded from), `snap/`, `truth/`, `gate-*.txt`, `selector-history.log`.

## What is and is not persisted on green

Persisted (survives pod restarts, node reboots, image re-pulls): APIs, revisions and gateway
artifacts, applications, subscriptions, consumer keys and secrets, DCR clients, users and roles,
rate-limit policies, key manager config, refresh tokens and authorization grants, the registry and
its search index, keystores, and all logs including analytics.

Not persisted: anything written inside the container outside those four mounts (for example files
dropped into `repository/deployment/server` by hand, or extra jars). The gateway rebuilds its
deployed APIs from the database on every start, which the restart test covers. In-memory throttle
counters start from zero after a restart.

Not carried over from blue: sign-in sessions, authorization codes and refresh tokens that blue
issued after the snapshot green was seeded from (`cat /root/apim-bluegreen/seed/TAKEN_AT`). Access
tokens are self-contained JWTs signed with the same key, so tokens issued by blue keep working on
green until they expire; console users may have to sign in once more.

Not protected: the volume is a directory on this one node and there is no scheduled or off-node
backup. The PersistentVolume was switched to reclaim policy `Retain` after go-live, so deleting
the PVC no longer deletes the directory (a volume re-created by `reseed.sh` or by hand starts as
`Delete` again: `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'`).

## Backup and restore of green

A consistent, verified copy of the live databases, without stopping anything (tested once after
go-live, result in `/root/apim-bluegreen/snap/green-live-1`):

    cd deploy/apim/scripts
    python3 truth.py collect https://127.0.0.1:30443 /root/apim-bluegreen/truth/bk.json
    APIM_SNAPSHOT_SELECTOR=app=wso2am-green bash snapshot.sh bk
    python3 validate.py /root/apim-bluegreen/snap/bk /root/apim-bluegreen/truth/bk.json

The copy holds hashed passwords and client secrets: keep it in a mode-700 directory. It does not
contain the keystores (`security/` on the volume; unchanged from the image today) or the search
index (rebuilt on demand).

Restore (gateway is down for about three minutes):

    kubectl -n apim scale deploy wso2am-green --replicas=0
    kubectl -n apim delete pvc wso2am-green-data
    bash seed.sh /root/apim-bluegreen/snap/bk          # only accepts a validated snapshot
    kubectl -n apim apply -f ../green/pvc.yaml
    kubectl -n apim scale deploy wso2am-green --replicas=1

A green pod that finds its volume empty and no armed seed refuses to start (init container `seed`
fails with an explanation) rather than serving blank or outdated databases.

## Re-running

All scripts run on the VM from `deploy/apim/scripts/`, need `kubectl` and `python3`, and read the
admin credentials from the ConfigMap in memory. `validate.py` needs the helper pod
(`kubectl apply -f deploy/apim/tools-pod.yaml`; `/root/apim-bluegreen/snap` must exist).

- Is green still a copy of blue, and switch if so: `bash go_live.sh`. Exit 3 = blue changed since
  the seed. Test APIs whose name or context starts with `weave`, `sample` or `e2e` are tolerated
  (the Weave runtime re-creates them: `POST /v1/gateway/resync`, called by the script when the
  runtime answers on 127.0.0.1:8790).
- Blue changed: `bash reseed.sh` (new snapshot, validation, wipes ONLY green's volume, restarts
  green, both gates, restart test), then `bash go_live.sh`. Refuses while green is live. After a
  rollback to blue, this pair is also the way forward again; whatever was created on green in the
  meantime is discarded with its volume, so take a backup of green first if it matters.
- From nothing: `python3 green_config.py apply`, `bash snapshot.sh s1`, `python3 truth.py collect
  https://127.0.0.1:30443 /root/apim-bluegreen/truth/s1.json`, `python3 validate.py
  /root/apim-bluegreen/snap/s1 /root/apim-bluegreen/truth/s1.json`, `bash seed.sh
  /root/apim-bluegreen/snap/s1`, `kubectl apply -f ../green/`, then `python3 gate.py --label
  first-boot`.
- Config change on green later: edit `/root/apim-bluegreen/green/deployment.toml`, update ConfigMap
  `apim-conf-green`, `kubectl -n apim rollout restart deploy/wso2am-green`. A restart of green takes
  about two minutes during which the gateway is down if green is live.
- Search listings in Publisher/DevPortal look wrong: raise `re_indexing` by one in green's
  `deployment.toml` and restart green.

## Retiring blue later

Blue costs 1 CPU / 2 Gi of requests and is the instant rollback. Its value drops with every change
made on green. When you no longer want to roll back:

    kubectl -n apim scale deploy wso2am --replicas=0      # keeps the object; nothing else changes
    kubectl -n apim delete pod apim-tools                 # helper pod, only needed for validate.py

Do not delete ConfigMap `apim-conf` unless `scripts/green_config.py` is no longer needed (it derives
green's config from it; the scripts fall back to `apim-conf-green` for credentials). Do not rename
green: the Service selector `app: wso2am-green` is what makes it live. `kubectl apply` of the old
blue Service manifest would silently point the Service back at blue: if that manifest lives
anywhere, change its selector first.
